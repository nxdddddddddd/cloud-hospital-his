# 云医院 HIS 数据库设计说明

## 1. 设计目标与范围

本数据库用于支撑学生作业中的门诊完整流程：

```text
挂号 → 医生接诊/病历 → 检查、检验、处置申请或处方
     → 收费 → 医技执行或药房发药 → 结果查看/诊断
```

数据库采用 MySQL 8.0.16+、InnoDB 和 `utf8mb4`，复用 RuoYi 的账号、角色、菜单和日志。业务部分共 **22 张表**，不包含真实医保结算、复杂药库管理或患者自助端。

## 2. 文件与执行顺序

| 文件 | 作用 | 是否必须 |
|---|---|---|
| `sql/his_cloud.sql` | 创建数据库及 22 张业务表 | 是，首次执行一次 |
| `sql/ruoyi_system.sql` | RuoYi 权限、菜单、日志及员工账号外键 | 是，首次执行一次 |
| `sql/quartz.sql` | RuoYi 定时任务表 | 是 |
| `sql/his_demo_data.sql` | 岗位账号、目录和虚构患者演示数据 | 作业演示建议执行，可重复执行 |

不要对已有数据库重复执行 `his_cloud.sql` 或 `ruoyi_system.sql`：前者会阻止覆盖已有库，后者会重建 RuoYi 表。`his_demo_data.sql` 仅用于已有完整结构的库，不负责创建表。

初始化后应有 **53 张表**。`his_cloud.sql` 中 `employee.sys_user_id` 先预留，待 `sys_user` 创建后在 `ruoyi_system.sql` 末尾建立物理外键，解决两表的创建顺序依赖。

## 3. 表分组

| 分组 | 表 | 说明 |
|---|---|---|
| 基础目录 | `department`、`employee`、`regist_level`、`scheduling`、`settle_category` | 科室、员工、号别、排班、结算类别 |
| 诊疗目录 | `disease`、`medical_technology`、`drug_info` | 疾病、检查/检验/处置项目、药品 |
| 患者就诊 | `register`、`medical_record`、`medical_record_disease` | 每次挂号一行；一次挂号最多一份病历，可关联多种疾病 |
| 医技申请 | `check_request`、`inspection_request`、`disposal_request` | 一行一个项目，保存申请、执行人、结果和状态 |
| 药品处方 | `prescription` | 一行一种药品，使用请求键和行号标识一张批量处方 |
| 收费退费 | `charge_order`、`charge_item`、`payment_record`、`refund_record`、`refund_item` | 收费单、收费明细、支付、退款及退款明细 |
| 药品库存 | `drug_stock`、`stock_movement` | 当前库存和不可重复的出入库流水 |

核心关系：

```text
employee 1 ──── n register 1 ──── 1 medical_record
                  │                         │
                  │                         n medical_record_disease n ──── 1 disease
                  ├── n check_request / inspection_request / disposal_request
                  ├── n prescription
                  └── n charge_order 1 ──── n charge_item
                                             │
                                             └── 1 payment_record 1 ──── n refund_record
```

`employee.sys_user_id` 对应 RuoYi `sys_user.user_id`。登录密码只保存在 RuoYi，不在员工表重复保存；未开通登录账号的员工允许该字段为空。`sys_user_id` 使用与 `sys_user.user_id` 相同的有符号 `BIGINT`，避免外键类型不兼容。

## 4. 关键字段设计

### 4.1 状态流转

- `register.visit_state`：`1` 已挂号 → `2` 医生接诊 → `3` 看诊结束；未看诊可转为 `4` 已退号。
- 医技申请：`UNPAID` → `PAID` → `EXECUTING` → `COMPLETED`；未缴费可 `CANCELLED`，允许退费时转为 `REFUNDED`。
- 处方：`UNPAID` → `PAID` → `DISPENSED`；退药后为 `RETURNED`，符合规则再转为 `REFUNDED`；未缴费可 `CANCELLED`。
- 收费单：`PAID` → `PARTIAL_REFUNDED` → `REFUNDED`。
- 库存流水：`RECEIPT` 入库、`DISPENSE` 发药、`RETURN` 退药。

数据库用 `CHECK` 限制枚举值、正金额、正数量、非负库存以及完成执行时必填的人员/结果。**状态能否流转由 Service 在事务中再次判断**，不能仅依赖 `CHECK`。

### 4.2 金额与历史快照

价格使用 `DECIMAL(12,2)`，药品数量和库存使用 `DECIMAL(12,3)`，禁止用浮点数保存金额。挂号、申请和处方均保存开立时单价，收费明细保存项目名称、数量和收费单价，使目录以后调价不会改变历史账单。

`charge_item.amount = ROUND(quantity * unit_price, 2)` 由 `CHECK` 校验；单总额、退款总额、支付金额是否一致由 Service 在事务内汇总校验。

### 4.3 幂等与业务追溯

`request_key` 防止重复挂号、收费、退款或开立申请；批量申请和处方使用 `(request_key, line_no)` 唯一定位明细。`request_hash` 由 Service 对完整规范化请求计算，用于识别“同一请求键却提交不同内容”。

`charge_item` 的 `source_type + source_id` 指向挂号、医技申请或处方，是应用层多态引用，因此不能对五个来源表同时建立普通外键。Service 必须校验来源存在、属于同一挂号且未重复收费。

`refund_item.charge_item_id` 唯一，保证一条收费明细最多全额退款一次。`stock_movement` 通过业务键和处方行唯一约束防止重复发药/退药。

## 6. 索引与完整性

- 业务编码建立唯一索引，如科室编码、号别编码、项目编码和药品编码。
- 挂号按 `(employee_id, visit_date, noon, visit_state)` 索引，支撑医生待诊列表和午别号额统计。
- 医技申请按 `(register_id, state)` 索引，支撑就诊详情；按项目和状态索引，支撑执行列表。
- 处方按 `(register_id, drug_state)` 索引；收费单按挂号和时间索引；库存流水按药品和时间索引。
- 基础目录使用 `delmark` 停用；诊疗、收费、库存流水不允许物理删除。普通外键默认 `RESTRICT`，避免误删被业务引用的主记录。

号额属于并发业务：SQL 唯一索引不能表达“某医生某午别最多 N 人”，Service 应锁定号别或专用号额记录，统计未退号挂号后判断容量，并在同一事务内插入挂号。


### 7.2 实际导入结果

已在 **MySQL 9.6.0** 上完成一次完整导入验证（2026-11-07）：

| 检查项 | 结果 |
|---|---|
| 表数量 | 53 张，符合预期 |
| 外键 | 48 个，全部建立成功 |
| CHECK 约束 | 57 个，全部生效 |
| 字符集 | `utf8mb4_0900_ai_ci`，中文无乱码 |
| 演示数据 | 1 名患者、7 名员工、2 张收费单、6 条收费明细、2 条处方 |
| 演示脚本重跑 | 退出码 0，无重复数据，可安全重复执行 |

约束负向测试（故意写入非法数据，均被拒绝）：

| 场景 | 实际拦截 |
|---|---|
| `visit_state = 9` | `ck_register_1` 拒绝 |
| 收费金额与数量单价不符 | `ck_charge_item_5` 拒绝 |
| 库存改为负数 | `ck_drug_stock_1` 拒绝 |
| 员工引用不存在科室 | `fk_employee_1` 拒绝 |
| 重复挂号幂等键 | `uq_register_1` 拒绝 |
| 重复处方请求键与行号 | `uq_prescription_1` 拒绝 |
| 未完成执行却标记完成 | `ck_check_request_4` 拒绝 |

**跨表金额一致性未被数据库拦截**（例如直接改 `charge_order.total_amount` 而不改明细）。这是设计边界：`CHECK` 只能校验单行，收费总额与明细合计、退款额与退款明细、库存与流水必须由 Service 在同一事务内校验。

导入过程仅有 MySQL 9.x 的弃用警告，不影响运行：

- `Integer display width is deprecated`：RuoYi 脚本中的 `bigint(20)`、`int(4)` 写法，MySQL 8.0.19 起弃用。
- `VALUES function is deprecated`：演示脚本的 `ON DUPLICATE KEY UPDATE ... VALUES(col)` 写法，建议后续改为 `AS new` 别名语法。

### 7.3 手动复核语句

```sql
SELECT COUNT(*) FROM information_schema.tables
WHERE table_schema = 'his_cloud_completed'; -- 53

SELECT r.case_number, r.real_name, e.realname AS doctor, r.visit_state
FROM register r JOIN employee e ON e.id = r.employee_id
WHERE r.case_number = 'DEMO0001';

SELECT source_type, item_name, quantity, unit_price, amount
FROM charge_item ORDER BY id;

SELECT d.drug_name, s.on_hand
FROM drug_info d JOIN drug_stock s ON s.drug_id = d.id ORDER BY d.id;
```

## 8. 设计边界

本作业数据库不通过触发器代替业务层，也不声称仅靠表结构解决全部并发和权限问题。必须由后端完成登录鉴权、当前医生/操作人身份获取、跨表状态校验、金额汇总、库存扣减和事务提交。现有 `MedicalTechService` 仍按前端传入姓名寻找执行人，后续应对接 RuoYi 当前登录用户，不能将此作为生产级身份校验。
