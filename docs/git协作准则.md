## 🛠️ 团队 Git 协作准则

**📝 核心理念**：
团队采用小步快跑的团队模式，省略 PR（Pull Request）审核环节，所有成员均拥有直接向主分支推送代码的权限。这要求我们在**推送到远端前，必须对自己分支的代码质量、可运行性负责**。

### 1. 分支管理策略

为保证成员各自的负责部分不互相干扰，采用以下分支管理策略：

- **`main` 分支（主分支）**：仅存放**编译通过、可运行**的代码。严禁直接在 `main` 上编写未完成的功能。
- **`feature/姓名缩写-功能`（开发分支）**：每个人的独立分支，主要使用的开发分支。开发完成后合并回main。
  - *示例：`feature/xm-login`、`feature/xh-upload`*
- **`hotfix/姓名缩写-问题`（修复分支）**：专门用于紧急修复 `main` 分支发现的 Bug，修复完成后合并回 main。

------

### 2. 每日标准流水线 

为了减少冲突，请严格遵守以下步骤：

#### 第一步：同步

开始写新功能前（每次merge之后），先更新本地主分支，确保本地与远程同步：

```bash
git status               # 【可选】确认状态，确保提示 "working tree clean" (没有未提交的修改)；若存在未提交的更改，应切换到自己的功能分支后提交更改（具体步骤见后文）
git checkout main        # 切换到本地主分支
#git pull -u origin main #-u用于设置上游分支，设置过上游分支就可以简化push和pull的步骤。【注】git clone会自动把远程的默认分支设为本地同名分支的上游，也就是说如果执行过git clone，无需再次设置，直接执行下一步的代码即可
git pull                 # 【仅限于设置了上游分支的情况，push同理】从远程服务器拉取组员昨天的最新代码
```

#### 第二步：分支开发

从最新的 `main` 创建自己的功能分支：

```bash
git checkout -b feature/yourname-task # 创建并切换到新分支
# ...进行代码编写...
git status                            # 【可选】确认状态，看看自己改了哪些文件
git add . # 将修改加入暂存区
git commit -m "feat: 增加XX接口"       # 提交到本地历史记录。""中的内容格式详见4.Commit信息格式化
```

**在这个分支上，你可以频繁 commit（即不断重复“编写代码-add-commit”的过程），但这绝不意味着你要立刻 push。** commit 是在你自己的电脑上进行保存，每完成一个小逻辑、修复一个拼写错误、重构一段函数甚至是删除一行没必要的注释就可以commit 一次。它相当于后悔药，一旦代码变得难以修改，可以直接回退到上一次commit时的状态，而不用狂按撤回还不知道应该在哪停下。在你自己的 feature 分支上，哪怕你每一分钟 Commit 一次都没关系，这非常安全，出错了随时能回退。**直到负责的某个部分的功能开发完毕、自测运行无误后，再进入第三步**。

#### 第三步：合并前对齐

完成某部分功能后，准备合并回 `main` 之前，**必须**再次拉取远程最新代码，防止队友先你一步提交，提前解决可能的冲突：

```bash
git status                             # 【可选】确认状态，确保当前分支代码都已 commit 完毕，没有遗漏
git checkout main                      # 切换到main分支
git pull                               # 再次获取远端最新主干代码（获取队友的新进度）
git checkout feature/yourname-task     # 切回你自己的功能分支
git merge main                         # 在自己的分支上解决掉所有可能的冲突
```

#### 第四步：正式合并

确认本地运行无误后，合并推送：

```bash
git checkout main                       # 切换到main分支
git merge feature/yourname-task         # 将你测试无误的功能合并入 main
git status                              # 【可选】最后检查，确认当前在 main 分支，并且一切正常
git push                                # 🚀 真正推送到远程共享库（全团队可见）
git branch -d feature/yourname-task     # 【可选】养成良好习惯，删除本地已经合并完的功能分支，保持环境清爽
```

### 3. 原子化提交与推送规范

- **本地原子化**：支持你在开发分支高频提交（参考第二步的循环）。
- **远程完整化**：当你执行 `git push origin main` 时，必须保证当前代码是**编译通过、可正常启动**的。
- **禁止中间态**：严禁推送“写了一半、运行会报错”的代码到 `main` 分支。
- **🚫 严禁提交环境/临时文件**：绝对不要提交 node_modules/、.env（包含本地密码/秘钥）、编译产物（如 dist/）。用 git status 时如果看到它们变成红色，说明 .gitignore 没配置好，**千万不要执行 git add .**。（理论上应该没有问题，因为我已经配置过.gitignore了。但是如果在add与commit中看到了巨量的文件更改，请保持谨慎。）

### 4. Commit 信息格式化

统一采用 `类型: 描述`，方便大家查阅历史：

| **类型 (Type)** | **具体场景**                                                 | **示例**                               |
| --------------- | ------------------------------------------------------------ | -------------------------------------- |
| **feat**        | **(Feature) 纯粹的新功能**。只要你写了之前没有的业务逻辑、新页面、新接口，就用这个。 | feat: 增加购物车结算模块               |
| **fix**         | **(Bug Fix) 修复问题**。不管是测试提出的 Bug，还是你自己发现的报错，只要是修漏洞就用它。 | fix: 修复移动端导航栏遮挡文字的bug     |
| **docs**        | **(Documentation) 纯文档修改**。只改了 README.md、接口文档说明，没有动任何一行业务代码。 | docs: 更新 README 中的本地启动步骤     |
| **style**       | **(Style) 代码格式调整**。只改了空格、缩进、删除了多余的空行、加了分号。**注：不包括 CSS 样式的修改，改 CSS UI 算 feat 或 fix** | style: 统一将双引号替换为单引号        |
| **refactor**    | **(Refactor) 核心重构**。指的是：**代码逻辑变了，但功能没变，也没有修 Bug**。比如你觉得原来写得太乱，重新整理了一下提取成了公共组件。 | refactor: 提取登录和注册公用的表单组件 |
| **perf**        | **(Performance) 性能优化**。专门为了让页面加载更快、让代码跑得更节省内存而做的修改。 | perf: 优化首页大图的加载速度           |
| **test**        | **(Test) 测试相关**。新增或修改测试用例，完全不影响生产环境代码。 | test: 增加密码校验工具类的单元测试     |
| **chore**       | **(Chore) 打杂/配置**。项目构建工具、配置文件（如 package.json、.gitignore、webpack配置）的变动，与具体业务代码无关。 | chore: 升级 axios 依赖包版本至 1.0     |

> *坏例子：`git commit -m "update"`*
>
> *好例子：`git commit -m "feat: 实现用户上传头像功能"`*
>
> 其实也不用太严格，稍微分分得了

### 5. 冲突处理与禁令

当你和队友修改了同一个文件的同一行代码，Git 无法判断该保留谁的，就会产生冲突。

解决冲突会比较麻烦，预防最大，但真出冲突了也不是无计可施：

**🚫 绝对禁令**：

- **禁止使用 git push --force 或 git push -f**。这会直接抹除队友的代码，造成严重的代码丢失事故。

- **遇到冲突 (Conflict)**：

  1. **git status**：发生冲突时，运行git status，提示 both modified 的红字文件就是需要你手动解决的冲突文件。

  2. **使用工具解决**：使用 VS Code 或 WebStorm 的源代码管理面板。点击冲突文件，编辑器会高亮显示：

     - Current Change（当前分支你的代码）
     - Incoming Change（来自 main 分支队友的代码）

  3. **人工抉择**：根据逻辑选择“保留当前”、“保留传入”或“两者保留”。（纯手动文本修改务必删掉系统生成的 <<<<、====、>>>> 符号）。

  4. **验证并提交**：

     ```bash
     git status      # 再次确认还有没有漏掉的冲突文件
     git add .       # 标记冲突已解决
     git commit      # 完成合并提交 (此时不用加 -m，直接保存系统弹出的信息即可)
     ```

  5. **重新运行**：处理完冲突后，**必须重新运行项目**，确认功能正常后再继续。

### 6. 常见场景与救急命令

- 遇到突发情况，**第一步永远是先敲 git status 确认当前处于哪种状态**，然后再对号入座找后悔药：

  #### 💊 场景 A：代码写得一团糟，想彻底扔掉（还没 add）

  - **现象**：git status 显示文件名是**红色**。

  - **痛点**：改了一下午发现思路全错，手动撤销太麻烦，想让这个文件恢复到上次 Commit 的样子。

  - **急救命令**：

    ```bash
    # 放弃单个文件的修改
    git restore <文件路径>
    # 放弃当前目录所有文件的修改（删了找不回）
    git restore .
    ```

  #### 💊 场景 B：把不该传的文件 add 了（还没 commit，撤回add）

  - **现象**：git status 显示文件名是**绿色**。

  - **痛点**：手滑敲了 git add .，结果发现把 node_modules 或者私密配置文件也加进去了，此时不要 commit

  - **急救命令**：

    ```bash
    # 把文件从暂存区踢出来，撤回add（文件变回红色，代码修改还在，只是不准备提交了）
    git restore --staged <文件路径>
    ```

  #### 💊 场景 C：刚敲完 commit 瞬间后悔了（还没 push, 撤回 commit）

  * **现象**：刚刚执行完 git commit -m "xxx"，但突然想起来有个重要 Bug 没修，或者 Commit 信息写了错别字。 

  * **痛点**：不想保留这次错误的 Commit 记录，想把它“撤销”，但不想把辛苦写的代码弄丢。

  * **急救命令：**

    ```bash
    # 若是初次提交出错：删除 HEAD 指针，让 Git 回到“还没人提交过”的原始状态
    git update-ref -d HEAD
      
    # 🟢 方案 1（最推荐）：只撤回 Commit 动作，保留所有代码，且代码仍在暂存区（绿字状态）
    git reset --soft HEAD^
      
    # 🟡 方案 2：撤回 Commit 动作，保留代码，但把代码打回工作区（红字状态）
    git reset HEAD^
      
    # 🔴 方案 3（核弹级，慎用！）：撤回 Commit，并且把刚写的代码全部直接删除
    git reset --hard HEAD^
    ```

  #### 💊 场景 D：大翻车！错误的代码已经 push 到远程主分支了

  * **现象**：不仅 commit 了，还手快敲了 git push origin main。结果队友一拉代码，项目跑不起来了。 **前提**：代码已经共享给了全团队。 **痛点**：此时**绝对不能用 git reset**！如果强行抹除远程历史，队友下次提交时会爆出无法挽回的幽灵冲突。你需要一种“优雅且合法”的反悔方式。

  * **急救命令：**

    ```bash
    # 查看历史记录，找到你那次错误提交的 Commit ID（比如 a1b2c3d...），复制前 7 位即可。按 q 退出查看
    git log
    
    # 撤销那次提交（用一个相反的新提交来抵消错误）
    git revert <Commit ID>
    
    # 将撤销操作推送到远程
    git push origin main
    ```
    
    **💡 revert 是怎么工作的？**
    它**不会**删掉你那次错误的提交记录，而是**聪明地新建一个“完全相反”的 Commit**。
    比如你刚才的错误 Commit 是“新增了A文件，删除了B文件”，执行 revert 后，Git 会自动帮你写一个新的 Commit，内容是“删除A文件，恢复B文件”。这样既把 Bug 修了，又保全了团队的 Git 历史时间线，安全无痛。

  #### 💊 场景 E：忘记切分支，直接在 main 上写了半天代码

  * **现象**：在 main 分支上写了很多代码，还没有 Commit。

  * **痛点**：团队规范严禁直接在 main 提交代码，但我不想把刚刚写的代码删掉重写。

  * **急救命令**（乾坤大挪移）：

    ```bash
    git stash                   # 把写好的代码打包（工作区变干净了）
    git checkout -b feature/xx  # 创建并切换到你该去的正确功能分支
    git stash pop               # 把打包的代码释放到新分支上，完成后可以继续开发
    ```

  #### 💊 场景 F：本地有改动，但需要紧急拉取远程重大更新

    - **现象**：功能没写完，执行 `git pull` 时报错 `Your local changes... would be overwritten by merge`。

    - **痛点**：远程主分支有必须立刻同步的代码（如接口变更或重大 Bug 修复），但你本地的功能只写了一半，还没到 commit 的时候，不想为了切换分支而勉强 commit 一个半成品。

  - **急救命令**：

    ```bash
    git stash -u              # 连同新文件一起打包藏起来
    git pull                  # 此时工作区干净了，丝滑拉取远程更新
    git stash pop             # 把自己的代码弹出来，继续开发
    ```
    
    **💡 stash注意事项：**
    使用 `git stash` 的核心前提是文件必须处于 Git 的**跟踪（Tracked）**范围内。对于新创建的文件，如果没有执行过 `git add` 将其加入暂存区， `git stash` 会直接忽略它，导致切换分支时该文件仍留在工作区甚至造成冲突。

    为了确保万无一失，可以使用 `git stash -u`（即 `--include-untracked`），这能强制 Git 同时打包那些尚未报到的新文件。此外，务必记住 `stash` 是一个本地堆栈，它不属于任何特定分支，恢复时若产生冲突，Git 会保留该记录，而不自动删除，此时你需要手动解决冲突，并执行 `git stash drop` 来清理。

  #### 💊 场景 G：刚刚 Commit 完，发现错别字 / 漏加了一个文件

  - **现象**：已经执行了 git commit -m "feat: xxx"，还没 push。

  - **痛点**：不想因为少加了一个文件，又产生一条多余的垃圾 Commit 记录。

  - **急救命令**：

    ```bash
    # 有点复杂，懒得弄就别弄了，垃圾commit就垃圾commit吧
    git add <漏掉的文件>        # 先把漏掉的文件加上
      git commit --amend        # 将这次的修改“悄悄塞进”上一次commit里
    # 此时终端会进入类似 vim 的文本编辑器界面，让你修改上一次的 commit 信息：
    # 按 i 进入编辑模式修改文字 -> 按 Esc 退出编辑 -> 输入 :wq 并回车保存退出。
    # （如果你只想改文件不想改说明文字，可以直接执行 git commit --amend --no-edit）
    ```

  #### 💊 场景 H：本地彻底玩坏了，想破罐子破摔

  - **现象**：冲突解决乱了，各种乱七八糟的历史记录，自己都不知道在哪个时空了。

  - **痛点**：只想把本地所有修改全扔掉，让代码变得跟远程仓库里的 main 分支**一模一样**。

  - **急救命令**（⚠️ 警告：执行后本地未推送的所有代码将全部消失）：

    ```bash
    git fetch --all                  # 下载远程仓库所有的最新进度
    git reset --hard origin/main     # 用远程的 main 分支无情碾压并覆盖本地的所有代码
    ```
